# 求职邮件申请链识别复盘与设计讨论

> 状态：讨论稿，不代表已经实施。本文只复盘问题并提出设计边界，不修改当前程序行为。

## 1. 问题本质

JobMailDesk 当前面对的不是普通文本分类问题，而是一个实体消歧与事件归属问题：

- 邮件描述的是哪家企业；
- 属于哪个招聘项目、事业群或批次；
- 对应哪个岗位或职位编号；
- 是一次新申请，还是已有申请的后续节点；
- 是同一事件的提醒、改期和取消，还是相同阶段的新事件。

单封邮件经常不包含完整答案。例如“我们已收到你的申请”只有企业和阶段，没有岗位、项目或职位编号。此时如果立即生成独立申请链，就会产生重复；如果仅凭公司名称合并，又可能把同公司多个岗位串错。

因此，系统目标不应是“每封邮件都必须立即归类”，而应是：

1. 有强证据时自动归并；
2. 有唯一上下文时延迟归并；
3. 证据冲突或候选不唯一时进入待确认；
4. 永远不以公司相同作为充分合并条件。

## 2. 已出现的错误类型

### 2.1 通用网申回执被建立为独立申请

样例：

```text
【京东校招】我们已收到你的申请，请及时关注后续进展
```

邮件没有岗位和项目。系统按单封邮件建立了“京东｜岗位待确认｜网申”链；18 分钟后的 JDS 测评又建立 JDS 链，形成重复。

根因：缺少跨邮件上下文和延迟决策机制。

### 2.2 同一项目因岗位字段缺失或写法变化被拆链

同一 JDS 流程中，有的邮件只写 JDS，有的邮件带具体岗位，有的邮件完全不写岗位。如果申请键直接包含原始岗位文本，就会形成多个 `application_id`。

根因：申请身份和展示字段混在一起。岗位名称可以补全或变化，但申请身份不应随展示文本改变。

### 2.3 邮件页脚中的项目列表污染主项目

京东邮件正文可能说明“投递 JDS/TET/TGT 多个人才项目时只需作答一次”。如果扫描全文看到 JDS，就可能把主题明确为 TET 的邮件错误标成 JDS。

根因：没有区分主题、正文核心区域和通用页脚的证据权重。

### 2.4 同阶段新事件覆盖旧任务并继承完成状态

任务键曾只包含申请链、事件类型、阶段和轮次。不同 Message-ID 的新测评可能撞上旧测评任务，从而继承旧任务的 `done` 和 `completed_at`。

根因：申请身份与事件实例身份没有分开。

### 2.5 母公司、事业群和招聘主体混淆

网易雷火、网易互娱可以在企业总览中统一为网易游戏，但不能因此进入同一申请链。类似问题也可能出现在集团、子公司、事业部和区域招聘主体之间。

根因：企业归一化、招聘项目和法律/业务主体没有分层。

### 2.6 操作说明或流程文字被识别为岗位

“请前往个人中心应聘记录进行修改”“确认投递的是某事业群校招职位”等句子曾被岗位提取规则捕获。

根因：只有正向岗位模式，缺少岗位负面词典和字段上下文约束。

### 2.7 邮件链与人工台账形成两份进展

邮件只能识别“JDS｜岗位待确认”，人工台账已有“2027 JDS 新星计划-产研项目管理”。两者没有共享稳定身份时，会在进展页显示为两条链。

根因：人工台账被当作另一个展示来源，而不是申请身份的补充事实源。

### 2.8 解析器重放与旧进程争写

新版和旧版同时运行时，不同解析器版本会反复清理去重游标并覆盖任务文件，造成已经修正的数据再次回退。

根因：单实例只约束同版本窗口，没有对数据目录写入者建立版本租约。

## 3. 建议的数据模型

应明确分开四种身份：

```text
CompanyIdentity      企业身份
ApplicationIdentity  一次真实投递/招聘申请
EventIdentity        一次测评、笔试、面试或材料截止事件
MessageIdentity      一封具体邮件
```

推荐关系：

```text
一家公司
  └─ 多个申请 Application
       ├─ 一个网申回执 Event
       ├─ 一个或多个测评 Event
       ├─ 多轮面试 Event
       └─ 每个 Event 可对应多封提醒/改期邮件 Message
```

`Message-ID` 只能解决重复邮件，不能代表申请链；阶段名称只能描述事件，不能代表事件实例。

## 4. 申请身份的证据优先级

### 一级强标识：可以自动合并

- 企业招聘系统中的申请 ID；
- 职位编号，例如 `J101273`；
- 明确项目代码，例如 `JDS`、`TET`；
- 邮件中的 requisition ID、candidate application ID；
- 同一招聘系统提供的稳定通知或投递记录编号。

### 二级组合标识：满足唯一性时自动合并

- 标准企业 + 招聘项目 + 招聘年份；
- 标准企业 + 事业群 + 职位编号；
- 标准企业 + 标准岗位 + 招聘批次；
- 无字段的网申回执 + 短时间内唯一的具体项目后续邮件。

### 三级弱标识：只能辅助排序，不能单独合并

- 相同发件人域名；
- 收件时间接近；
- 邮件主题相似；
- 同一阶段；
- 同一企业名称；
- 岗位文本的模糊相似度。

### 禁止自动合并的冲突

- 不同职位编号；
- 不同项目代码，例如 JDS 与 TET；
- 不同事业群，例如雷火与互娱；
- 不同招聘年份或批次，且没有明确迁移关系；
- 同一公司存在两个以上候选申请，邮件又没有岗位/项目信息；
- 人工明确标记为独立申请。

## 5. 推荐的申请身份注册表

需要的不是一份覆盖全行业的“岗位语言库”，而是一份用户本地、可维护的申请注册表。建议每次投递形成一条：

```yaml
application_key: jd-jds-2027-product-project-management
company: 京东
company_aliases:
  - 京东校招
sender_domains:
  - jd.com
recruiting_project: JDS
recruiting_year: 2027
business_unit:
role: 产研项目管理
role_aliases:
  - 2027 JDS 新星计划-产研项目管理
job_code:
submitted_at: 2026-08-03
source: 岗位投递决策台账
status: active
```

程序识别邮件时先查询注册表：

1. 强标识命中现有申请，直接关联；
2. 只有企业和阶段时，查询时间附近的活跃申请；
3. 候选唯一且不存在冲突，允许关联；
4. 候选超过一个，进入“选择属于哪个申请”的待确认界面；
5. 用户确认一次后，保存模板和别名，后续相同格式自动识别。

现有《岗位投递决策台账》可以作为注册表的人工入口，但不应直接依赖自由文本行。长期应增加稳定 `application_key`、职位编号、项目代码和招聘年份字段。

## 6. 是否需要语言库或 NLP 模型

### 通用中文分词库：优先级低

Jieba、HanLP 等可以帮助切词，但不能可靠判断“JDS/TET 是项目列表还是当前项目”，也不能判断两个相似岗位是否属于同一真实投递。它们无法替代身份数据。

### 本地受控词典：需要

建议拆成可审计配置：

```text
companies.yml      企业、品牌、招聘主体和发件域名
programs.yml       JDS/TET、事业群、校招批次和项目代码
roles.yml          岗位标准名、别名、职位编号和负面模式
mail_templates.yml 已核验邮件模板及字段位置
```

词典必须是精确、可回归、可人工修订的，不能使用无边界的字符串相似度自动扩张。

### 岗位表：需要，但必须是“个人投递岗位表”

通用岗位分类表只能用于展示归类，例如产品、运营、研发；真正用于申请链识别的应是用户已经投递的岗位表，包括企业、项目、年份、事业群、岗位原名、标准岗位名和职位编号。

### LLM：只能作为可选建议层

模型可用于从陌生模板中提出候选字段，但不能直接写入正式申请链。输出必须包含证据句和置信度，并经过确定性约束或人工确认。

Core 仍应无需 API 和境外网络运行。

## 7. 推荐的解析流程

```text
邮件只读获取
  ↓
模板分区：主题 / 核心正文 / 字段表 / 页脚
  ↓
提取候选：企业、项目、岗位、职位编号、年份、阶段、时间
  ↓
标准化词典：精确别名和负面词
  ↓
查询本地申请注册表
  ↓
硬冲突过滤
  ↓
候选评分与唯一性判断
  ├─ 强标识唯一：自动关联
  ├─ 上下文唯一：延迟关联
  └─ 多候选/低置信度：待确认
  ↓
建立 Event，再关联 Message
```

## 8. 建议的置信度与行为边界

| 证据 | 建议行为 |
| --- | --- |
| 申请 ID 或职位编号完全一致 | 自动关联 |
| 企业 + 项目代码 + 年份一致 | 自动关联 |
| 无字段回执，2 小时内只有一个具体项目后续邮件 | 延迟自动关联，并记录推断原因 |
| 企业 + 标准岗位一致，但同企业存在多个活跃项目 | 待确认 |
| 只有企业、发件人和时间接近 | 待确认，不自动合并 |
| 项目代码、职位编号或事业群冲突 | 禁止合并 |

每次自动关联应保存：

- 使用了哪些证据；
- 置信度；
- 是邮件明确事实还是上下文推断；
- 用户是否确认过；
- 可撤销的原始归属。

## 9. 如何减少未来错误

1. 首次配置时可选关联《岗位投递决策台账》，生成申请注册表。
2. 新投递优先由用户或邮件回执创建申请身份，后续事件只能挂接，不能随意重建身份。
3. 无字段邮件先进入短暂的 `unresolved` 缓冲区，完成本轮扫描后再做上下文关联。
4. 同一公司存在多个活跃岗位时，禁止只按公司和时间自动归并。
5. 所有人工纠正都生成局部规则，但规则必须展示作用范围和撤销入口。
6. 解析器升级只重算“归属建议”，不得静默覆盖用户确认过的申请身份。
7. 数据目录增加写入租约，阻止不同版本进程同时重放和写入。

## 10. 建议的实施顺序

### 第一阶段：身份层

- 建立 `applications` 注册表；
- 引入稳定 `application_key`；
- 把岗位投递台账转换为结构化输入；
- 区分明确字段和推断字段。

### 第二阶段：解析层

- 邮件模板分区和证据权重；
- 企业、项目、岗位、职位编号本地词典；
- 通用回执的延迟归属；
- 硬冲突规则。

### 第三阶段：人工确认闭环

- 待确认界面显示候选申请与证据；
- 支持“属于已有申请 / 新建申请 / 忽略”；
- 人工确认后沉淀局部模板规则；
- 支持撤销错误合并。

### 第四阶段：可选智能增强

- 本地或 API 模型只负责字段候选和模板建议；
- 不允许模型绕过身份约束直接合并；
- 用匿名回归邮件评估准确率、误合并率和待确认率。

## 11. 成功标准

- 相同 Message-ID 永不重复建任务；
- 相同职位编号和申请 ID 稳定进入同一申请链；
- 不同项目代码、事业群或职位编号永不自动串链；
- 无项目邮件在候选不唯一时不会自动合并；
- 人工确认过的归属不会被解析器升级覆盖；
- 邮件任务和人工台账共享同一个稳定申请身份；
- 每次自动归属都有可读证据和撤销方式；
- 误合并率优先于自动归类率：宁可待确认，不可串错岗位。

## 12. 当前建议结论

下一步不应继续为单家公司追加临时 `if company == ...` 规则。应先建立通用申请身份层，再把京东 JDS/TET、网易事业群、百度职位编号等规则作为词典和测试样例接入。

推荐选择：

1. 以个人岗位投递表作为申请身份注册表的来源；
2. 使用本地精确词典，不引入通用 NLP 运行依赖；
3. 增加扫描批次后的延迟归属和冲突检测；
4. 对低置信度邮件提供人工选择，而不是自动建立或合并申请链；
5. LLM 仅作为后续可选的字段提取建议层。
