# 企业、项目与阶段标准化

JobMailDesk Core 不依赖模型判断企业名称。邮件解析后会经过一套本地、确定性、可回归测试的标准化词库。

## 三层规则

1. **通用招聘词黑名单**：`在线`、`AI`、`27届校招`、`校园招聘`、`测评通知` 等不能成为企业名称；命中后继续尝试发件人名称。
2. **企业精确别名表**：只合并已经人工核验的等价名称，例如 `多益网络招聘 → 多益网络`、`小鹏集团 → 小鹏汽车`。不使用模糊字符串相似度。
3. **招聘项目与事业群**：母企业用于总览归类，事业群保留在 `recruiting_project`。例如网易雷火和网易互娱都归入 `网易游戏`，但分别保留 `雷火事业群`、`互娱事业群`，不会进入同一申请链。
4. **岗位受控别名**：只维护人工核验的岗位等价关系，例如 `TET 管理培训生（综合方向） → TET 综合方向`。职位编号优先于岗位文本；官网操作说明、个人中心提示和“确认投递的是某事业群校招职位”等说明句不能成为岗位。
5. **双来源归并**：邮件任务和人工台账先统一企业、事业群和岗位别名，再按稳定 `application_id` 归并。匹配成功后台账只补充当前进展与下一步，不再生成第二张虚拟申请卡。

实现位于 `src/job_mail_desk/normalization.py`，每条新增别名或黑名单规则必须同时提供匿名回归样例。

## 申请链与台账同步不变量

- 同一邮件 `source_message_hash` 只能对应一个任务；重复扫描只更新原任务。
- 同一申请链在一轮扫描结束后只同步一次台账，使用合并后的当前节点；旧测评或旧面试不得覆盖更新的群面、后续面试或 Offer。
- 企业使用母公司身份，事业群进入招聘项目；网易雷火与网易互娱可以同属网易游戏，但项目范围不互相归并。
- 同公司不同岗位保持独立；无法确认岗位时保留“岗位待确认”，不靠模糊相似度强行合并。
- 解析规则版本变化时自动回放最近 30 天，而不是只清空去重游标后继续使用 3 天窗口。

## 为什么不用模糊匹配

相似名称不一定是同一招聘主体。`网易雷火` 与 `网易互娱` 属于同一母品牌下的不同招聘项目；子公司、事业部和集团品牌也可能拥有独立流程。错误合并会把岗位、笔试和面试轮次串到另一条申请链，因此 Core 只接受精确别名和带上下文的事业群规则。

## 无法确定时

当主题中的名称只是招聘通用词，并且发件人也不能提供可靠企业名时，记录使用 `公司待确认`，进入待确认视图。程序不会为了填满字段而猜测企业。

## 时间语义

- `邀请于 A，于 B 失效`：解析为有效窗口 `start_at=A`、`end_at=B`。
- `收到邮件后 N 小时/天内`：以邮件收取时间换算绝对截止时间。
- 明确结束时间已过：转入企业进展历史，不进入待办、周历或月历。
- 没有可验证时间：保留在待确认，不虚构日期。
