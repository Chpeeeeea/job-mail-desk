# 维护、更新与发布规则

本文是 JobMailDesk 的日常维护手册。`PROJECT_RULES.md` 保存不可破坏的产品约束；本文规定一次修改如何从本地进入 `main`，以及何时生成用户可下载的 Release。

## 1. 三种“更新”必须分开

| 名称 | 完成标志 | 用户能看到什么 |
| --- | --- | --- |
| **阶段提交** | Commit 已推送到功能分支 | GitHub 保存了修改，但默认首页和安装包可能不变 |
| **仓库更新** | Pull Request 已通过检查并合并到 `main` | 默认源码、README 和文档更新 |
| **产品发布** | 版本标签触发 Release，六个资产验证通过 | 用户可以下载新的 Windows/macOS 安装包 |

规则中的“阶段性进展必须推送”不等于每个文档修改都必须生成安装包。只有应用行为、安装内容、兼容性或用户体验发生可交付变化时，才创建新的产品版本。

## 2. 分支与主线

- `main` 是唯一正式主线，必须保持可构建、可回滚。
- 不直接在 `main` 上开发；从最新 `main` 创建短期功能分支。
- 分支命名：
  - `agent/<主题>`：由本地 Agent 实施的阶段工作；
  - `feature/<主题>`：新功能；
  - `fix/<主题>`：普通修复；
  - `hotfix/<主题>`：已发布版本的紧急修复；
  - `docs/<主题>`：纯文档调整。
- 一个分支只处理一个可说明、可验证、可回滚的目标。
- 合并后删除远端功能分支；标签和 Release 永久保留。

## 3. 变更分类与版本号

JobMailDesk 使用 `MAJOR.MINOR.PATCH` 语义化版本号。

| 类型 | 示例 | 版本处理 |
| --- | --- | --- |
| 纯文档、截图、注释 | README、许可说明、维护规则 | 合并 `main`，通常不单独发包 |
| 修复 | 解析错误、退出异常、UI 错位、重复任务 | PATCH：`0.4.1 → 0.4.2` |
| 向后兼容的新功能 | 新视图、新邮箱适配、新设置项 | MINOR：`0.4.x → 0.5.0` |
| 破坏兼容的变化 | 数据格式不兼容、删除公共 CLI | MAJOR；`1.0` 前必须在 Release Notes 显著说明 |
| 安全紧急修复 | 凭据、隐私、更新链路漏洞 | 立即发布 PATCH，不等待常规周期 |

不得覆盖、移动或重新指向已经发布的版本标签。发布内容有误时，保留原记录并发布更高版本修复。

## 4. 标准维护流程

### A. 开始前

1. 从 `main` 拉取最新远端状态，确认工作树干净。
2. 判断变更属于文档、修复、功能、安全还是发布维护。
3. 检查 `PROJECT_RULES.md`、相关架构文档和现有测试。
4. 创建单一目标的功能分支。

### B. 实施中

1. 使用匿名样例，禁止把真实邮箱、授权码、Message-ID、私人 URL、手机号或个人路径写入仓库。
2. 修改解析、去重、状态或 Obsidian 同步时必须补回归测试。
3. 修改 UI 时必须检查正常尺寸、高 DPI、缓存首屏、空状态和退出流程。
4. 修改用户可见行为时同步更新 README、快速开始或对应说明，不能只改代码。
5. 将用户可感知的变化写入 `CHANGELOG.md` 的 `[Unreleased]`，按 `Added / Changed / Fixed / Security / Removed` 分类。

### C. 本地验收

最低检查：

```powershell
uv run pytest
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\secret-scan.ps1
git diff --check
```

按风险追加：

- 邮件/解析：只读 IMAP、时间边界、重复邮件、改期、忽略和完成状态回归；
- UI：正常启动、缓存启动、白屏、正常退出、单实例、DPI 与关键视图；
- Markdown/Obsidian：稳定 ID、勾选往返、手写区保护和重复导出；
- 打包：Windows 本地包内容检查，macOS 交给真实 GitHub Runner；
- 更新功能：只读 Release API、缓存、通道筛选和无网络降级。

### D. Commit、Push 与 Pull Request

1. 只暂存本阶段相关文件，不混入无关本地修改。
2. Commit 使用简短动词描述结果，例如 `Fix duplicate task revival`。
3. 推送功能分支并创建 Pull Request。
4. PR 默认可先设为 Draft；实现和本地验收完成后必须改为 Ready for review。
5. PR 描述必须包含：变化、原因、用户影响、验证结果、隐私/数据影响和回滚方式。
6. Windows x64、macOS arm64、macOS x64 三项检查全部通过后才允许合并。
7. 合并采用 merge commit，保留阶段提交；合并后确认 `main` 与远端一致。

### E. 是否创建 Release

满足任一条件时创建新版本：

- 应用代码或用户可见行为发生变化；
- 安装包内容、运行依赖或平台支持发生变化；
- 修复会影响用户现有任务、邮件解析、同步、启动、退出或安全；
- 需要让已安装用户收到版本通知。

仅 README、截图、项目规则或开发文档变化时，通常只合并 `main`，并留在 `[Unreleased]`；下一个产品版本统一带入安装包。

### Release Freeze（本地验收闸门）

- 从一轮功能开发或问题集中处理开始，到本地验收清单全部关闭之前，持续处于 Release Freeze。
- Freeze 期间允许提交、推送、PR、三平台 CI 和本地 `-rc` 测试包，但禁止创建 `vX.Y.Z` 标签或 GitHub Release。
- 同一轮用户反馈应尽量合并验证，不能每修一处就发布一个安装包。中间版本由本地 RC 或 Actions artifact 承担。
- 只有以下项目全部满足后，维护者才能明确标记 `release-ready`：
  - 本轮范围冻结，不再等待已知反馈或数据样例；
  - 自动化测试、秘密扫描、`git diff --check` 全部通过；
  - 真实邮件只读回放、重复扫描、状态持久化和 Obsidian 同步已验证；
  - UI 视觉、启动、缓存、退出、单实例与本地 self-contained 包已验证；
  - Changelog、Release Notes、版本号和升级说明已完成。
- `main` 可以在 Freeze 期间接收已经验证的阶段 PR；合并主线不等于立即发布。Release 应在本轮全部本地验证结束后一次性完成。
- 安全、凭据泄露或数据损坏类紧急问题可以跳过常规批次等待，但仍必须完成与风险相称的本地验证并发布更高 PATCH。

## 5. 产品发布流程

1. 确认 Release Freeze 已解除并记录 `release-ready`，再决定新版本号并同步更新项目版本字段。
2. 将 `[Unreleased]` 中属于本版本的内容移动到 `## [X.Y.Z] - YYYY-MM-DD`。
3. 创建 `docs/RELEASE_NOTES_vX.Y.Z.md`，写清亮点、修复、升级方式、已知问题、签名状态和数据兼容性。
4. 更新 README 中的版本号、下载链接和预览版提示。
5. 依据 `docs/RELEASE_CHECKLIST.md` 完成本地和远端验收。
6. 合并发布 PR 到 `main`。
7. **只在合并提交上**创建并推送 `vX.Y.Z` 标签。
8. GitHub Actions 自动构建并发布：
   - Windows x64 ZIP + SHA-256；
   - macOS Apple Silicon ZIP + SHA-256；
   - macOS Intel ZIP + SHA-256。
9. 从 Release 重新下载资产，核对文件名、数量、哈希和启动行为。
10. 未完成代码签名、Apple 公证或三天真实试运行时，只能发布为 prerelease。

Release 创建后禁止静默替换 ZIP。需要修复时发布新的 PATCH 版本，保证用户看到的版本与校验值始终可追溯。

## 6. 更新兼容性

- 程序目录与用户数据目录必须分离；覆盖应用不得删除本地任务、配置、凭据或 Obsidian 文件。
- 任务 Markdown 是事实层。新增字段应提供默认值，旧任务必须仍可读取。
- 数据迁移必须可重复执行；中途失败不得留下不可启动状态。
- SQLite 和首屏缓存必须可重建，不能成为唯一事实来源。
- 删除或重命名配置项时必须提供兼容读取或明确迁移说明。
- 更新通知只提示公告和下载入口，不自动下载、解包、覆盖、执行或重启程序。

## 7. 紧急修复与回滚

### 紧急修复

1. 从当前发布标签或最新 `main` 创建 `hotfix/<主题>`。
2. 只修改必要范围，增加复现测试。
3. 更新 Changelog 和 Release Notes，发布更高 PATCH 版本。
4. 隐私、凭据或数据损坏问题优先于常规功能排期。

### 回滚

- 未合并：关闭 PR 或追加修复 Commit，不重写已经共享的历史。
- 已合并未发版：使用新的反向 Commit，经测试后再合并；不强推 `main`。
- 已发版：保留原 Release，在公告顶部标记已知问题，并尽快发布修复版本。
- 禁止删除用户数据来“解决”升级问题；必须先提供备份和恢复路径。

## 8. 维护节奏

- 每次阶段：更新 Changelog、测试、秘密扫描、提交、推送、PR 检查。
- 每月一次：检查直接依赖、GitHub Actions、Python 3.12 兼容性和过期文档。
- 每个 Release 前：完整执行发布清单和三平台构建。
- 每个 Release 后：核对六个资产、版本公告、更新提示与下载链接。
- 稳定版前：至少三天真实环境试运行，记录白屏、启动、退出、扫描和同步情况。

## 9. 完成标准

一项阶段工作只有同时满足以下条件才算完成：

- 目标功能或文档已经实现；
- 风险对应的测试通过；
- `CHANGELOG.md` 已记录；
- 秘密扫描和 `git diff --check` 通过；
- Commit 已推送；
- PR 的三平台检查通过并合并到 `main`；
- 若属于产品发布，Release 六个资产已验证；
- 用户能从 README、快速开始或 Release Notes 知道如何使用和升级。
